### Shipping

Read the installed plugin's [RUNTIME.md](../../../RUNTIME.md) first. Its native tool, model, path, and session-authorization rules apply. The user merges; this port never merges, enables auto-merge, or enters a merge queue.

**You own the verified handoff. Verify each PR independently, prepare only the verified run from the root for the user to merge, then keep your hands off the stack.**

This is the half after `playbooks/babysit.md`.

1. **Resolve the forge, then verify each PR independently before handoff.** GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve the repository, use `origin pr` for every read. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). One verifier per PR, each a native subagent with an exclusive local worktree, runs the change the way a user would with the matching control skill (`browser-use` or `control-cli` bundled with this plugin), parent against head, and posts `PASS`, `PASS+NOTES`, or `FAIL` on that PR. Only a verdict from an agent that did not write the code counts. Green CI and an approving bot review are not verdicts. Pick each subagent's reasoning level for the job, per the Subagents section of `$poteto-mode`.
2. **Hand off only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without `PASS` or `PASS+NOTES`. The PRs below it are the run, and the top one is the ceiling. A verified PR above an unverified one waits, because the user cannot merge it without the code below it. One whose branch neither holds nor needs that code can move onto trunk on its own. It needs a fresh verdict first, because its old one ran with that code beneath it and trunk does not have it.
3. **Re-check that the verdicts still describe the code.** A verdict covers a patch, and a chain rebase moves every PR above it to a new SHA without failing any check. Compare `git patch-id` at the verdict SHA with the current head before trusting an older verdict. When the patches differ only in tests, docs, or lint config, a lane's result stands if what it ran builds the same at both SHAs apart from noise. Noise is a difference that also shows up between two builds of the verdict SHA, or an embedded commit SHA. Report each kind of noise with its files. The change itself still gets fresh checks and a review, because the old verdict never saw it. A lane with no build output, such as a dev server, cannot show this, so rerun it, and re-verify anything else that drifted.
4. **Prepare the bottom PR for the user. Do not merge it.** Fetch current trunk. Rebase the lowest verified branch onto the exact trunk tip when needed, push it, and retarget only that PR to trunk with `origin pr edit <pr> --base <trunk>` or `gh pr edit <pr> --base <trunk>`. Re-run step 3 after the push. Never run `origin pr merge` or `gh pr merge`, and never arm `--auto`. Report the exact merge command for the user, and say that a merge command can report success when a queue only queued the PR. After the user merges, confirm the PR reads merged with trunk as its base. Then retarget the PR whose base was the merged branch, move its patch onto the merge result, and push with `--force-with-lease`. The verdict covers the patch, not its commits, so step 3 decides whether the verdict survives. Hand that PR off once its checks pass and its verdict survives.
5. **Leave the stack alone while the user merges.** Step 4's move of the next PR is the only change to a branch or base. When watching was requested, use `scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom-to-top>` on GitHub per RUNTIME.md until it reports `COMPLETE` at the ceiling. On Origin, re-read the current PR with `origin pr view <pr> --checks` each time `origin pr checks <pr> --watch` returns. A base that moves to trunk when its parent merges is expected. If a merge stalls, find out why before you change anything.
6. **Stop at the ceiling.** Extending the run takes new verdicts, so it is a new pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what you handed the user and how you confirmed readiness, what landed during an authorized watch, and what the next gap needs.
